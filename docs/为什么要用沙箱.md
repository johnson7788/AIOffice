1. 沙箱是「池化预热」的，创建时还不知道是哪个用户
start() 里 SandboxPoolAsync(max_idle=_POOL_SIZE) 提前热好一批空沙箱，请求来了 _pool.acquire() 抓一个（sandbox.py:100）。可 bind mount
必须在容器创建那一刻就指定路径，而那一刻根本没有 user——你要挂 uploads/<user_id>，就得放弃池化、每个用户冷启一个专属沙箱，热启动的收益全没了。

2. opensandbox 是「远程 SDK」抽象，不是本地 docker
它走 ConnectionConfig(domain, protocol)，文件是通过 sandbox.files.write_file API 推进去的。而且 PoolCreationSpec 只暴露 image 和
network_policy（sandbox.py:67-70）——根本没有 volume/mount 字段。bind mount 只有「沙箱和你在同一台机器」才成立；你现在能 docker exec
进去纯属它恰好跑在本地。换成远程/云上跑，挂载直接失效，而同步照样能用。

3. 隔离 / 爆炸半径
terminal 是高权限任意代码执行。RW 挂载 = agent 生成的代码能直接读改删你的真实文件，一个路径逃逸或 bug
就打到源文件。现在是：按需拷贝需要的那一个文件进去，沙箱用完被 reaper 回收（sandbox.py:189 空闲释放），真实文件始终是 source of
truth，写回也走受控的 sync_sandbox_to_workspace。

4. 池化沙箱会跨用户复用，残留挂载会把 A 用户的文件泄漏给 B。

---
什么时候挂载确实更好？ 如果你的部署就是本地、单用户、不要池化，那挂载能删掉那两个 sync 工具和"按需同步"这套
dance，确实更简单——代价是丢掉池化预热 + 那层隔离。

但当前用 opensandbox 的 PoolCreationSpec 连挂载入口都没有，要挂载得先离开这套池化 SDK（比如自己 docker run -v 起容器）。

所以问题其实是：你的目标部署是「本地单用户」还是「多租户/可远程」？
- 本地单用户 → 我可以帮你把沙箱换成自管 docker run -v uploads/<user>:/workspace，删掉 sync 工具。
- 多租户/未来上云 → 保持现在的按需同步，别挂载。
